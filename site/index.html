The finish line

You're done when all six of these are true.

  • Each parent has one account with all their kids under it, and each kid has their own record.
  • The front desk sees who is active and who is past due when a kid checks in.
  • Members, families, classes, attendance, levels, waivers and billing records live in The LAB's own app.
  • Staff open it from a link on their phones and sign in.
  • You export and store every Spark record before you cancel Spark.
  • The non-renewal notice reaches Spark at least 30 days before the term ends.

Setup

About 30 minutes, once.

Install

  • Claude Code, signed in. Use the VS Code extension if you'd rather not work in a terminal.
  • Node.js 22 or newer.
  • Git and a GitHub account.
  • VS Code.
  • The Claude in Chrome extension, so Claude can open websites and test the app in a real browser.
  • An empty folder named lab-spark, opened in VS Code with the Claude Code panel open.

Ground rules

  • Never paste the Spark security key, passwords, card numbers or member details into a prompt.
  • Use made-up sample members until step 8 puts real data behind a sign-in.
  • Read each approval before you say yes. Take extra care with delete, push and send.
  • Pushing to main publishes the site. Do it on purpose.

Parent and child accounts

The whole app sits on this. Settle it in step 1, and check it again after each step.

How it works

  • Parent account: one sign-in per parent. It holds contact details, billing and the signed waiver.
  • Child accounts: each kid sits under a parent and has their own class, level, attendance and membership status.
  • A family can have two parents. Both see and manage the same kids.
  • One bill per family. It covers every kid's membership.
  • One waiver per family, naming each kid it covers. Adding a kid adds them to it.
  • Front desk: search a kid and see the parent, or search a parent and see every kid. Check in siblings with one tap.

Decide these in step 1

  • Is a membership per kid or per family? Can one sibling be frozen while another stays active?
  • Sibling discount: how much, and from which kid on?
  • What does a parent see when they sign in: schedule, attendance, levels, bills?
  • Who can pick up a kid, and is that stored on the family?
  • When a kid turns 18 or a parent account closes, what happens to the kid's record?
Already in the LAB app

The lab-skill-unlocks database stores families, guardians (more than one per family, one marked primary) and athletes under each family. Step 8 builds on it.

4

Get the brand kit

1 hour · Claude reads the website

A brand kit is the logo files, colors and fonts in one folder. If you don't have one, Claude builds it from thelab.life. It reads the exact colors and fonts from the page's code, downloads the logo files the site uses, and cleans them up so they work on any background.

1 · Pull the brand from the website

Prompt
Build a brand kit for The LAB from thelab.life. Open it in the browser and read the real colors (hex) and fonts from the page styles, not by eye. Download every logo file the site uses, SVG first and PNG if there's no SVG, into brandkit/source, with a list of the URL each one came from. Write brandkit/README.md: each color and what the site uses it for, fonts and weights, the logo files, and the font licenses.

2 · Cut out the logo backgrounds

Prompt
Make the logos usable anywhere. For each logo: if it's an SVG, remove any background shape so only the logo itself is left. If it's a PNG or JPG with a background, cut the background out to transparent, and trace it to an SVG if the shapes are simple. Don't redraw or change the logo. Save navy, white and black versions to brandkit/logos as SVG and as transparent PNG at 2400px wide. Check that each PNG's background is transparent.

3 · Look at it

Prompt
Make brandkit/index.html showing every logo on a white, a navy and a photo background, plus the colors and fonts. Pull it up in the browser for me.
Check the logos yourself

Look for a white or gray box around a logo, rough edges, or a missing tagline. File names can be wrong: on thelab.life, the file named "Black" contains the white logo. An SVG from the site is better than cutting a logo out of a picture, because it stays sharp at any size.

A kit made this way already exists in the lab-skill-unlocks repo, in brandkit/. You can copy that folder and use prompt 3 to check it.

Type this

Prompt
Set up a design system from our brand kit in brandkit/ and the rules in <path to lab-skill-unlocks>/app/DESIGN-SYSTEM.md. Navy #0F0E54, cyan #22BCED for actions, mint #C2E6DB for secondary actions, ink #090D19 for text, Argentum Sans headings and Work Sans body. Use the logos from brandkit/logos. Two token layers (brand colors, then names the UI uses), a component library, a style-guide page, and a lint that fails if any UI color is off the tokens.

8

Connect real data

A few sessions · needs accounts

Shared data across phones, real sign-ins, card payments and automatic texts all need a server. The LAB app (the lab-skill-unlocks repo) has one, plus a Spark webhook that receives member status, past-due and join dates, check-in, and a consent log. Reuse it before building new.

Type this

Prompt
<path to lab-skill-unlocks> is our existing LAB app. It has a Supabase backend with families, guardians and athletes, a Spark webhook, check-in and a consent log. Read it and tell me what we should reuse. Then plan how to move parent accounts, their kids, memberships and attendance onto it behind real sign-ins, where a parent sees only their own kids. Don't change that repo until I approve the plan.
Billing needs the most setup

Recurring card and bank payments need a processor (Stripe or similar), a server and your accounts. Decide who bills before you build it: the new app, or another system. Ask Spark in writing whether stored cards can move to the new processor. If they can't, families re-enter cards.

9

Cut over and cancel Spark

Plan 45+ days ahead of the term end

This step is a checklist. Work through it in order.

  • Find the term end date in the Spark contract. Put the non-renewal deadline, 30 days before it, on the calendar.
  • While the account is still paid, export: All Contacts with every column (including the fields that link parents to kids), Past Due Memberships, each waiver and form's submissions (CSV), signed membership agreements, and attendance and rank history.
  • Ask Spark's data team in writing for a full archive. Don't count on the 30-day window after the contract ends.
  • Waivers: get an Arizona attorney to review the app's waiver text, and the insurance carrier's sign-off, before it replaces Spark's form.
  • Run both systems side by side for two weeks. Check that the active and past-due counts match each day.
  • Move billing, then send the non-renewal notice in writing.
Ask Claude to check the exports

Put the export files in a gitignored folder and ask: "Compare these Spark exports with the app's data and list every parent, kid or waiver that's missing, and every kid not linked to a parent." Keep real member data out of the public repo.

Habits that make it work

The Axis app was built in about two days with ten prompts. These habits did most of the work.

Say the outcome

"So the desk knows who's past due before class" beats a list of buttons. Describe the job from the user's side.

Give it the material

Paste folder paths, links and file names. Claude opens and reads them.

Push back

"This feels basic. What do the best gyms use?" led to the research that put Axis level with Tint Wiz.

Say how you'll judge it

"Test it on live, not localhost" and "show me at phone size" catch bugs a summary hides.

State the standard

"Free, open source, just works" changed how Claude designed Axis's route planning. Say what you value in one sentence.

Commit at every working step

Say "commit this" whenever something works. A commit is a checkpoint you can go back to.

When it goes wrong

Problems the Axis build ran into, and the fix for each.

The live site is blank, but local works

The base path is the usual cause. Say: "The live site is blank. Check the base path and the 404 fallback for GitHub Pages, fix it, push, and test on live."

"node is not recognized" on Windows

Node isn't on the PATH. Reinstall Node from nodejs.org and restart VS Code, or tell Claude the error and let it fix the PATH for the session.

Buttons lost their colors

A long-running dev server can serve old styles. Say: "restart the dev server."

Claude says it's done and I'm not sure

Ask to see it: "Open every page at phone and desktop width, take screenshots, and show me any console errors." Read the screenshots yourself.

It keeps listing things it can't finish

Those rows need a server, accounts or your decision: payments, automatic texts, real sign-ins. Mark them "later" in the parity checklist, or do step 8.

The conversation got long and confused

Commit, then run /clear to start fresh. Claude rereads CLAUDE.md and the brief.

Commands worth knowing

/help lists commands. /init writes CLAUDE.md. /goal sets a finish line. /clear starts fresh. /code-review checks your changes for bugs before a big push.
